# c64-https v0.6.0

**For demonstration and educational purposes only. It is not cryptographically secure.**

Built from the commit tagged `v0.6.0`. Submodule pins (`tools/check_upstream_pins.py`):
- `libs/mlkem` v0.6.0 (new);
- `libs/nistcurves` v0.15.0 (unchanged);
- `libs/x25519` v0.16.0 (unchanged);
- ip65 `25a9c5a` (untagged, unchanged).

This release covers the merged PRs since v0.5.1: #306-#308, #310, #311 (build and rig fixes), #312-#315 (the post-quantum hybrid key exchange, below) and this release's packaging change. The main change: **both UCI images now offer the hybrid key exchange X25519MLKEM768.** They have completed fetches of the Wikipedia Commodore 64 article over it on hardware. `ip65-onchip` stays classic and is **not** byte-identical to v0.5.1 (see below).

**No classic UCI image ships any more.** `uci-onchip` and `uci-comb` are the same products as before with `PQ_HYBRID=1` added to their make arguments. To build the v0.5.1-style X25519-only UCI image, omit it: `make BACKEND=uci USE_NISTCURVES_ONCHIP=1 TRUST_STORE=1` (or `USE_NISTCURVES_ONCHIP_COMB=1`).

## Post-quantum hybrid key exchange

- The ClientHello offers `X25519MLKEM768` (0x11EC: ML-KEM-768 encapsulation key || X25519 share) first and `X25519` (0x001D) second; the server picks. A 0x11EC answer feeds `mlkem_ss || x25519_ss` into the handshake secret (draft-ietf-tls-ecdhe-mlkem, ML-KEM first). A 0x001D answer completes with X25519 alone, as before.
- **A server that picks X25519 does not get the v0.5.1 client.** KeyGen still runs on every connection; the ClientHello is about 1.2 KB larger and is sent in several sections; and the ServerHello is read by a stricter streaming reader (an empty session-id echo, exactly the two extensions we asked for, a malformed or oversize record header while waiting for the ServerHello is now fatal).
- ML-KEM-768 comes from `libs/mlkem` (c64-mlkem v0.6.0). Its code is staged in the PRG at `$A000` and copied to `$E000` at boot; the polynomial area is `$D000-$DFFF` (RAM under I/O) and the decapsulation-key scratch is the first 2,400 B of the TCP ring. Intermediates are scrubbed after KeyGen and after Decaps, and both shared secrets are zeroed once the handshake secret exists. `PQ_HYBRID` is refused on ip65, uci-m3 and the uci REU profile.
- **Cost** (U64E at 48 MHz, local OpenSSL 3.6.5 listener, release arguments plus `HTTPS_SNI`, time from the SYS trigger to client Finished, 0.5 s poll, n=3 each; the classic image is the same arguments without `PQ_HYBRID`):

  | image | classic (PQ_HYBRID off) | hybrid | difference |
  |---|---|---|---|
  | uci-onchip | 52.4, 52.1, 52.6 s (mean 52.4) | 55.2, 54.8, 54.6 s (mean 54.9) | **+2.5 s** (+4.8%) |
  | uci-comb | 41.0, 41.3, 40.6 s (mean 41.0) | 43.9, 43.1, 43.4 s (mean 43.5) | **+2.5 s** (+6.1%) |

  Whole Wikipedia fetch with the release PRGs, rig wall-clock: 191-192 s onchip, 220-222 s comb; the classic comb control took 218 s (n=1).
- **What it protects, and what it does not.** The hybrid changes the key exchange only: a passive recorder who later has a quantum computer cannot recover a session's keys from the recorded handshake unless it can also break X25519 or ML-KEM-768 (harvest now, decrypt later). **Authentication is unchanged and classical:** the server proves itself with ECDSA P-256, and the UCI images' only pin is trust-on-first-use of that leaf key. And the protection is only as good as its secrets: this client's DRBG is seeded from SID voice 3 and CIA timer noise, which is weak, and the ML-KEM seed and X25519 private key both come from it. Read this as a demonstration of the protocol path, not as quantum safety.
- Servers: OpenSSL 3.6.5 `s_server` and en.wikipedia.org negotiate 11EC with our hello (tables below); browserleaks.com did in an earlier live run. github.com and lwn.net do not offer 11EC (`openssl s_client -groups X25519MLKEM768` gets `handshake_failure`); a `uci-comb` fetch of github.com/robots.txt falls back to X25519 and completes.

## Other changes since v0.5.1

- PQ stages, in order: the sectioned ClientHello with 16-bit lengths and HelloRetryRequest refusal (#312); `libs/mlkem` pinned and placed behind `PQ_HYBRID=1`, link-only (#313); the streaming hybrid ServerHello, KeyGen in `tls_connect`, Decaps (#314); the hybrid key schedule (#315).
- The linker output no longer depends on the build locale (#311), a linker-config edit relinks the PRG (#306), a bare pytest is green on a uci or an ip65 build (#308), and the rig trampolines set the trust-store mode (#307). Docs: #303, #310.
- `tools/uci/rig_https_banner.py` prints `tls_kex_group`; `REQUIRE_KEX=EC` makes any other group part of the exit decision (`decide_exit`).

Rebuilt at each step: `1c377d34…` after #311 (link order only), then `e69bfce7…` from #312 on, unchanged by #313-#315. **#312 changed ip65 code**: it added the HelloRetryRequest check to the ip65 ServerHello parser and changed the shared ClientHello builder. **No handshake has been run on these ip65 bytes**: the VICE network rig needs a sudo rig-up that was not done for this release, so the image has only been booted to the banner (package-verify). ## What this release does NOT do

- **No certificate chain validation on the three 6510 images** (unchanged). The released UCI images pin by trust-on-first-use (`TRUST.A` / `TRUST.B` on `/USB1`); a build-time pin or a signed bundle needs a custom build. If the store cannot be used, they offer to continue unpinned. The ip65 image accepts any certificate whose signature verifies. On the M3 demo, the ESP32 verifies certificates against its own Mozilla CA store.
- **Server name validation is UCI-only.**
- **Entropy is weak** (see above).
- **The Wikipedia REU viewer demo does not link with `PQ_HYBRID=1`.** `make BACKEND=uci USE_NISTCURVES_ONCHIP_COMB=1 PQ_HYBRID=1 HTTPS_HOST=en.wikipedia.org HTTPS_PATH=/wiki/Commodore_64 HTTPS_BODY_TO_REU=1` overflows CRYPTO_HOT by 507 B. Build the demo without `PQ_HYBRID`.
- **A hybrid ServerHello sent as one record cannot be read** (the record buffer is 548 B); the client refuses it at once, leaving `tls_sh_err=$0E` (not shown on screen). Servers that honour max_fragment_length (OpenSSL, Wikipedia, browserleaks) split it. Front ends that ignore it, such as Cloudflare's and BoringSSL-based ones, are out of scope (Cloudflare also enforces a ~15 s deadline).
- **`ip65-onchip` is not network-validated at this release** (see above).
- **The C64 Ultimate was not validated for this release.** The last C64U run (v0.5.1, `uci-onchip` against Wikipedia at 64 MHz) did not reach a connection:
  - Its trust store could not be used, so the image printed `TRUST FAIL 02` and asked `CONTINUE UNPINNED? Y/N`. The UCI images keep their trust store (`TRUST.A` / `TRUST.B`) on `/USB1`, and that C64 Ultimate has no `/USB1` volume. That fits, but the cause was not investigated.
  - The path the rig typed arrived as `/wiki/.ommodore_64`.
  - No socket was opened ("NOT DIALLED").
